# Spark DAO on Base

Base implementation of the Spark DAO protocol.

This codebase is a protocol-focused migration from the earlier Solana implementation. It preserves the economic logic used in the paper and recasts it in an EVM-native form for Base.

## Scope

- `src/`: core contracts
- `test/`: Foundry test suites used for behavioural and gas validation
- `script/`: deployment and demo scripts
- `client/`: minimal `viem` client helpers and reproducibility checks
- `simulation_inputs/` and `simulation_outputs/`: fee assumptions and generated cost outputs

The main contracts are:

- `ResearchRegistry.sol`
- `TeachingRegistry.sol`
- `TeachingRewardDistributor.sol`
- `ResearchPositionToken.sol`
- `TeachingNftToken.sol`

## Current architecture

`ResearchRegistry` manages research assets, research positions, layer seal/advance
state, direct revenue escrows, position transfers, DAO buybacks, vault funding, and
per-stable reserved-unit accounting. In the full teaching deployment,
`TeachingRegistry` inherits this surface, so `RESEARCH_REGISTRY` and
`TEACHING_REGISTRY` can point to the same deployed registry address. A standalone
`ResearchRegistry` remains available for research-only demos and tests.

`TeachingRegistry` manages teaching lifecycle state: course types, scheduled teaching
sessions, first-round schedule freeze, collateral locks, second-round completion,
coordinator settlement decisions, settlement snapshot calculation, teacher redeem,
vault reserve accounting, and the stable-token transfer callback used by reward claims.

`TeachingRewardDistributor` is a separately deployed contract. It stores teaching
reward pools, tracks single-use claims, previews claimable amounts, handles single and
batch claims, and releases rounding dust once all effective snapshot shares have been
accounted for. A reward pool can only be recorded by its configured registry.

`ResearchPositionToken` and `TeachingNftToken` are minimal soulbound ERC-721-like
tokens. Their minter should be set to the registry and then locked after deployment.

## Reproducibility

Build and test with Foundry:

```bash
forge build --sizes --skip script
forge test -vv
npm run client:typecheck
npm run check:reproducibility-config
npm run simulate:teaching-cost
```

Gas calibration rows are generated by `TeachingGasCalibration.t.sol` and
`ResearchGasCalibration.t.sol`; the TypeScript simulation reads those CSVs and writes
`simulation_outputs/`. Do not hand-fill gas or cost outputs.

## Settlement model

Teaching settlement is claim-pull. A resolved teaching session records bounded reward
pools for its linked research assets, including the frozen stable asset, unlock time,
scheduled-time layer snapshot, and aggregate distributable reserve. Research position
holders then call `TeachingRewardDistributor.claimTeachingReward(teachingNftId, assetId,
positionId)` or the batch variant. Settlement cost is bounded by the number of linked
research assets; the current operating rule permits at most two linked research assets
per teaching session.

The position owner at claim time receives the reward. If a research position has been
transferred, the new holder claims. If it has been bought back, the DAO treasury holder
claims. Later authority rotation does not move already bought-back positions or their
claim rights.

Claim settlement is split across two contracts. The distributor validates the pool,
holder, unlock time, claim status, weighted claim amount, batch shape, and dust release.
It then calls back into `TeachingRegistry.settleTeachingRewardClaim`, which updates the
position's claimed units, releases vault-reserved units, and transfers the frozen stable
asset to the claimant. Direct calls to that callback are rejected unless they come from
the configured distributor.

## Stable assets and reserves

`daoState.stableAsset` is only the default for newly created objects. Course types,
teaching sessions, revenue escrows, reward pools, and research position buyback floors
freeze their stable asset when created. Vault reserves are tracked per stable asset via
`getVaultReservedUnits(stableAsset)`, with `fundDaoVaultFor` and `withdrawDaoVaultFor`
available for explicit multi-stable funding.

## Token minters

`ResearchPositionToken` and `TeachingNftToken` support `lockMinter()`. The intended
deployment flow is to deploy both token contracts, deploy the registry, set the registry
as each token minter, and then lock both minters. Registry authority rotation remains
available for DAO administration but cannot redirect token minting after the lock.

## Distributor wiring

`TeachingRegistry.setTeachingRewardDistributor` is an authority-only, one-time wiring
step. The registry checks `ITeachingRewardDistributor(distributor).TEACHING_REGISTRY()`
against its own address before storing the distributor, which catches common address or
deployment-order mistakes. This handshake does not prove the distributor bytecode is
benign; deployment authority still has to use the intended `TeachingRewardDistributor`
implementation.

## Treasury custody

`daoState.treasury` is the custody address for positions bought back by the DAO. It should
normally be a multisig or treasury account, not an operator hot wallet. Authority rotation
changes administrative control only; it does not move already bought-back research
positions or their future claim rights.

## Teaching fault settlement

The Base teaching registry uses a fault-contingent settlement rule for lessons that cannot be closed by ordinary two-sided completion:

- customer fault keeps half of the locked lesson price, refunds the other half, and pays the teacher `min(teacher salary, half price)` together with the returned teacher bond;
- teacher fault keeps half of the locked lesson price, refunds the other half, returns the teacher bond, pays no teaching salary, and records one remedial lesson owed on the same teaching record;
- research-linked rewards are not inferred from customer fault, but teacher fault can still fund research/IP rewards for the affected lesson and the remedial lesson from the retained half-price amount;
- teaching research share is capped at 25% on-chain so the teacher-fault branch remains solvent. The intended operating cap can be lower.

Remaining retained funds are left in the registry as service-guarantee reserve, not booked as a teacher or customer payout.

## Deployment

Deployment is split into three scripts:

1. `DeployTokens.s.sol`
2. `DeployRegistry.s.sol` deploys `TeachingRegistry`, deploys `TeachingRewardDistributor`,
   and wires the distributor into the registry
3. `SetTokenMinters.s.sol` sets and locks the token minters to the registry

Local end-to-end demos:

- `DemoResearch.s.sol`
- `DemoTeaching.s.sol`

## Configuration

Environment variables are listed in `.env.example`.
Project configuration is in `foundry.toml`.

For full teaching deployments, record the registry output as both `RESEARCH_REGISTRY`
and `TEACHING_REGISTRY`, and record the distributor output as
`TEACHING_REWARD_DISTRIBUTOR`. The client can inspect research and teaching registry
state without the distributor, but teaching reward preview and claim helpers require
`TEACHING_REWARD_DISTRIBUTOR`.

This live worktree is not a review-package or snapshot staging area. Snapshot packaging,
archival uploads, and supplementary bundle assembly are separate workflows.
